# REGLAS OPERATIVAS JARVIS — AUTOMEJORA INCREMENTAL

## OBJETIVO

Evolucionar de `intencion -> comando -> funcion -> ejecucion` a `intencion -> Goal -> Task/HTN -> State/Knowledge -> Graph -> Planner -> Plan -> Executor -> Verification -> State actualizado -> Replan`.

El desarrollo debe priorizar la corrección funcional, el orden lógico de dependencias, la integración progresiva y la comprobación del comportamiento en el entorno real. Los tests automatizados son necesarios, pero nunca sustituyen la verificación real de una capacidad que interactúa con el sistema.

# 1. FUENTES DE VERDAD Y ALCANCE

- El bloque ESTADO PERSISTENTE ACTUAL de `mejora/prompt_mejoraActual.txt` es la única fuente de continuidad y determina la unidad que debe trabajarse. El roadmap de `mejora/prompt_JARVIS_fases_estado.txt` define estructura, jerarquía y dependencias, no el estado actual. No usar README, historial, Git ni recuerdos de otros chats para escoger otra unidad.
- Un chat trabaja una sola unidad hoja: la hoja más profunda definida. No adelantar la siguiente. La hoja debe ser pequeña y verificable; si resulta demasiado grande, dividirla antes de implementarla, registrar la relación padre-hijas en `prompt_JARVIS_fases_estado.txt` y trabajar exclusivamente la primera hija pendiente.
- No avanzar mientras la hoja activa tenga pendientes. Una unidad padre solo se completa cuando todas sus hijas están completadas y verificadas. Una fase solo se completa si todas sus hojas están verificadas y `main.py` cumple cuando corresponda.
- Antes de iniciar el trabajo, leer `prompt_mejoraActual.txt`, este archivo de reglas y TODO `docs/README.md`; después consultar en `prompt_JARVIS_fases_estado.txt` solo las secciones necesarias para `CURRENT_WORK_UNIT` y abrir los archivos de código pertinentes.
- Consultar `docs/README_TESTS.md` antes de modificar tests y contrastar sus apartados con los cambios realizados.
- En ficheros grandes, localizar primero la clase, método o símbolo pertinente y ampliar la lectura únicamente cuando haga falta. Para búsquedas y análisis de archivos del proyecto, utilizar siempre `limit=2000`.
- No comenzar código hasta identificar la unidad activa, sus criterios de aceptación, las dependencias necesarias y la estrategia de verificación.
- `docs/README.md` es documentación técnica del código existente. `prompt_mejoraActual.txt` contiene el estado operativo; este archivo contiene las reglas; `prompt_JARVIS_fases_estado.txt` contiene el roadmap y los registros de trabajo. `docs/README_TESTS.md` documenta los tests existentes.
- Documentar en `docs/README.md` solo código nuevo o modificado que realmente lo necesite, en su apartado técnico: finalidad, contrato, uso, integraciones y comportamiento real. No documentar código preexistente solo por haberlo inspeccionado ni registrar fases, unidades, IDs de mejora, avances, fechas, historial, commits, resultados de ejecución o cierres de fase. Puede explicarse la finalidad y cobertura estática de los tests, pero README no es un registro de ejecuciones.
- Siempre que se modifique de forma relevante cualquier fichero dentro de `src/`, revisar obligatoriamente, al terminar los cambios, si `docs/README.md` necesita actualizarse para reflejar el código resultante. Contrastar la implementación final con el apartado técnico correspondiente y actualizarlo cuando hayan cambiado o aparecido aspectos documentables de su finalidad, contrato, uso, flujo o comportamiento. Si la modificación no cambia información técnica que deba constar en README, no realizar cambios innecesarios, pero efectuar igualmente la revisión. Toda actualización describirá exclusivamente hechos objetivos y el comportamiento real del código tal como queda después de la modificación; nunca incluir referencias a fases, unidades, IDs de mejora, avances, fechas, historial ni motivos temporales del cambio.
- Siempre que se añada o modifique de forma relevante cualquier fichero dentro de `tests/`, revisar obligatoriamente, al terminar los cambios, si `docs/README_TESTS.md` necesita actualizarse para reflejar los tests resultantes. Contrastar los tests finales con el apartado correspondiente y actualizarlo cuando hayan cambiado o aparecido aspectos documentables de su finalidad, cobertura, métodos o comportamiento. Si la modificación no cambia información técnica que deba constar en README_TESTS.md, no realizar cambios innecesarios, pero efectuar igualmente la revisión. Toda actualización describirá exclusivamente hechos objetivos y el comportamiento real de los tests tal como quedan después de la modificación; nunca incluir referencias a fases, unidades, IDs de mejora, avances, fechas, historial ni motivos temporales del cambio.
- Código actual y tests son la evidencia técnica primaria. Si código, README y prompt discrepan, no corregir la discrepancia por intuición: inspeccionar solo lo necesario, registrar lo contradictorio y la evidencia.
- No pedir archivos salvo que sean imprescindibles para la hoja o una discrepancia concreta.
- No inventar funcionalidades, fases, IDs, archivos, clases, métodos, APIs, coordenadas, offsets, tests, métricas ni resultados. Reutilizar implementaciones y contratos reales; no duplicar lógica ni crear APIs ficticias.
- No implementar una capacidad que ya exista sin haber identificado primero sus limitaciones reales y justificado la necesidad de modificarla.
- Las coordenadas y puntos UI son datos de percepción/calibración, no inteligencia ni reglas de decisión.
- No introducir ML, deep learning, RL u otra complejidad para aparentar inteligencia; utilizar IA, LLM o Vision cuando aporten valor demostrable.

# 2. PROHIBICIÓN ABSOLUTA DE GIT

- Está terminantemente prohibido ejecutar comandos `git` en cualquier circunstancia, sin excepciones y aunque sean de solo lectura. La prohibición incluye, entre otros, `git status`, `git diff`, `git log`, `git show`, `git blame`, `git branch`, `git switch`, `git checkout`, `git stash`, `git fetch`, `git pull`, `git push`, `git commit`, `git add`, `git reset`, `git rebase`, `git cherry-pick`, `git revert` y cualquier otro subcomando, opción, alias o variante de Git.
- También está prohibido invocar Git indirectamente mediante scripts, herramientas, extensiones, interfaces gráficas, automatizaciones o comandos encadenados; así como consultar o manipular `.git` (incluidos `HEAD`, `config`, `logs`, `objects`, `refs` e `index`) para examinar el estado, comparar cambios, obtener evidencias o alterar el repositorio.
- No crear commits ni realizar ninguna operación de versionado.
- Esta prohibición no se puede levantar por inferencia ni por conveniencia; solo podrá cambiarse si el usuario modifica expresamente estas reglas.
- Para analizar el proyecto, verificar cambios y obtener evidencia, utilizar exclusivamente los archivos de trabajo, el código actual, los tests y la documentación técnica permitida, sin recurrir a Git ni a sus datos.
- No proponer Git como solución alternativa, mecanismo de recuperación o procedimiento de diagnóstico.

# 3. TESTS Y SEGURIDAD DE VERIFICACIÓN

## 3.1. Principios de integridad

- Un test correcto que falla obliga a corregir el código de producción, no a debilitar el test.
- Está prohibido quitar asserts, ocultar errores, aceptar cualquier resultado, saltar casos o borrar pruebas para obtener PASS.
- Cambiar un test solo si está objetivamente mal, obsoleto por un cambio legítimo de contrato o contradice requisitos reales. Registrar el motivo y el contrato que justifica el cambio.
- Si un test fija correctamente un contrato todavía no implementado, registrar el fallo como tal, nunca como PASSED.
- Todos los tests, mocks, fixtures, datos y scripts cuyo objetivo sea probar, depurar o reproducir deben residir en `tests/`.
- No introducir código de pruebas, archivos temporales o datos de experimentación dentro de `src/` ni en los directorios de datos persistentes del usuario.
- No inventar rutas de tests. Verificar siempre las rutas reales dentro de `tests/` y qué módulos, clases y métodos ejecutan.
- Separar resultados unitarios, integración, verificación real y no regresión. Indicar conteos reales y baseline comparable cuando exista.
- No presentar resultados no ejecutados como pasados ni atribuir fallos de entorno a código sin evidencia.

## 3.2. Plan de verificación obligatorio antes de implementar

Para cada unidad:

1. Identificar el comportamiento concreto que debe obtenerse.
2. Identificar los módulos, clases, métodos y dependencias reales que intervienen.
3. Definir los criterios de aceptación observables.
4. Determinar los tests unitarios necesarios.
5. Determinar las pruebas de integración con componentes reales.
6. Determinar las pruebas en el entorno real del equipo.
7. Identificar los riesgos, efectos secundarios y recursos que pueden verse afectados.
8. Establecer cómo comprobar el estado anterior y posterior a cada operación.
9. Definir la limpieza segura de los recursos temporales creados por la prueba.
10. Registrar las limitaciones que impidan ejecutar algún escenario.

No implementar primero y dejar para el final la decisión de cómo comprobar que funciona.

La prueba debe estar vinculada al comportamiento real de la unidad, no simplemente al número de tests que se hayan escrito.

## 3.3. Categorías de verificación

Distinguir obligatoriamente estas categorías:

**A. Tests unitarios**

- Comprueban lógica, contratos, validaciones y resultados aislados.
- Utilizan datos representativos y fixtures controlados.
- No demuestran por sí solos el funcionamiento de APIs del sistema operativo, aplicaciones, ventanas, hardware o servicios externos.
- Registrar el resultado de forma independiente.

**B. Tests de integración**

- Comprueban la comunicación entre los componentes que realmente forman la funcionalidad.
- Siempre que sea viable, utilizar implementaciones reales de los componentes integrados.
- No sustituir mediante mocks un componente cuyo comportamiento se pretende verificar.
- Comprobar datos de entrada, salida, efectos y propagación de errores.
- Registrar las integraciones efectivamente ejecutadas.

**C. Verificación en el entorno real**

- Ejecutar la implementación de producción en el Windows real del equipo, utilizando las APIs, archivos, procesos, ventanas, dispositivos, servicios o aplicaciones reales afectados.
- Comprobar que la operación ocurre realmente y que su resultado es observable.
- No sustituir mediante mocks la funcionalidad que se afirma haber verificado.
- Registrar el escenario, procedimiento, resultado observado, limitaciones y evidencias.
- No afirmar compatibilidad universal a partir de una sola máquina o configuración.

Las tres categorías deben mantenerse separadas aunque todas resulten satisfactorias.

## 3.4. Política de mocks y simulaciones

- Los mocks, stubs y monkeypatches se permiten para aislar fronteras externas, provocar errores difíciles de reproducir o verificar llamadas que formen parte de un contrato.
- No pueden decidir por adelantado el resultado que el test afirma demostrar.
- No pueden sustituir la selección, validación o identificación del objetivo que se pretende probar.
- No pueden sustituir el escáner, repositorio, preflight, selector real de ventanas, lanzador, autorización, persistencia o verificación cuando alguno de esos elementos constituya el objeto de la prueba.
- Comprobar los estados antes y después y los efectos observables.
- Incluir controles positivos, negativos y pruebas de sensibilidad de protecciones críticas cuando sea seguro y viable.
- Cuando se simule una condición, ejecutar una prueba separada del flujo real siempre que dicha condición pueda reproducirse de forma segura en el equipo.
- Una prueba con Windows real no se considera una prueba real del componente si dicho componente ha sido sustituido por un mock.

## 3.5. Seguridad de datos y recursos

- Las pruebas destructivas o que cambien datos utilizarán directorios temporales o copias controladas y recursos creados por la propia prueba.
- Las pruebas de lectura del sistema completo serán de solo lectura.
- No alterar documentos personales, datos persistentes reales, configuraciones del usuario, archivos originales o bases de datos reales para fabricar escenarios.
- No borrar archivos desconocidos ni elementos descubiertos durante una prueba.
- No sobrescribir datos preexistentes para simular una operación.
- Cuando sea necesario probar persistencia, utilizar un almacenamiento temporal aislado o una copia controlada y comprobar que los datos originales no han cambiado.
- Los recursos creados por una prueba deben poder identificarse inequívocamente y su limpieza debe limitarse a esos recursos.
- No finalizar procesos ni cerrar ventanas preexistentes.
- No ejecutar pruebas que puedan afectar a la sesión del usuario, a sus datos o a otras aplicaciones sin un mecanismo seguro y verificable de aislamiento.

## 3.6. Verificación de inventario y escaneo global

Cuando una unidad afecte al inventario, escaneo, descubrimiento o clasificación del sistema de archivos:

- Ejecutar el código real sobre todos los volúmenes locales montados que el adaptador detecte dentro del alcance aprobado.
- Comprobar la detección real de volúmenes antes de iniciar el escaneo.
- Registrar cada volumen por separado.
- Registrar cobertura, exclusiones, errores, permisos, elementos inaccesibles, resultados parciales y tiempos cuando se midan.
- No afirmar que se ha escaneado todo el ordenador si existen volúmenes, directorios, subárboles o entradas que no se han inspeccionado.
- No elevar privilegios ni eludir permisos sin autorización explícita.
- Los elementos inaccesibles deben identificarse como tales, sin tratarlos como inexistentes.
- Evitar bucles por enlaces simbólicos, junctions, puntos de montaje o referencias circulares.
- Respetar los límites de alcance y exclusión definidos en la configuración real.
- No modificar, mover ni borrar archivos durante un escaneo de lectura.
- Contrastar los resultados del inventario con muestras comprobables del sistema de archivos real.
- Verificar que las rutas descubiertas existen y que los metadatos registrados corresponden a los elementos reales en el momento de la comprobación.
- Comprobar que el almacenamiento del inventario conserva los resultados correctamente y puede recuperarlos mediante su implementación real.
- Verificar los escaneos parciales, reanudaciones, cancelaciones y actualizaciones únicamente cuando la unidad correspondiente implemente esas capacidades.
- Diferenciar claramente entre elementos detectados, elementos inspeccionados, elementos excluidos, elementos inaccesibles y elementos clasificados.
- Un inventario no demuestra que una aplicación esté instalada, sea ejecutable, sea segura o pueda lanzarse.
- El descubrimiento de archivos o aplicaciones nunca constituye autorización para ejecutar elementos encontrados.

No utilizar los tests con directorios artificiales como única evidencia de que un escáner funciona sobre el sistema real.

## 3.7. Verificación de descubrimiento y lanzamiento de aplicaciones

Cuando una unidad afecte a aplicaciones:

- Utilizar una allowlist de aplicaciones inocuas instaladas en el equipo.
- Comprobar individualmente los destinos aprobados.
- No ejecutar en lote todos los `.exe`, accesos directos, URI, paquetes ni candidatos descubiertos.
- No confundir localizar una aplicación con demostrar que puede ejecutarse.
- Comprobar por separado resolución, validación mediante preflight, autorización, lanzamiento y resultado observable cuando las unidades correspondientes ya implementen esas capacidades.
- No declarar que una aplicación se ha abierto correctamente únicamente porque se haya devuelto un PID, una ruta, un identificador o una respuesta positiva de una función.
- Verificar el proceso y la ventana reales asociados al lanzamiento cuando el alcance de la unidad requiera comprobarlos.
- Identificar el proceso y la ventana creados por la prueba antes de interactuar con ellos.
- No cerrar ni terminar procesos o ventanas preexistentes.
- Limpiar exclusivamente los procesos y ventanas creados por la propia prueba cuya propiedad se haya demostrado.
- No probar candidatos desconocidos, aplicaciones críticas o destinos potencialmente destructivos como parte de una ejecución masiva.
- Obtener autorización explícita cuando una prueba pueda generar efectos externos, modificar datos, iniciar sesión, enviar comunicaciones o alterar el estado del sistema.

No declarar que JARVIS puede abrir cualquier aplicación en cualquier ordenador por haber probado unas pocas aplicaciones en un único equipo. Registrar la cobertura real por sistema operativo, tipo de instalación, tipo de lanzamiento y aplicación probada.

## 3.8. Evidencias reproducibles

Para cada verificación real, registrar cuando corresponda:

- Fecha y hora.
- Sistema operativo, versión y arquitectura.
- Versión de Python y dependencias relevantes.
- Comando o procedimiento ejecutado.
- Archivo, clase, método o componente real sometido a prueba.
- Escenario y recursos utilizados.
- Resultado esperado.
- Resultado observable real.
- Recuentos y métricas efectivamente obtenidos.
- Errores y advertencias.
- Limitaciones y elementos no comprobados.
- Estado de los recursos protegidos antes y después.
- Identificación de la prueba o artefacto de evidencia cuando exista.

Para pruebas gráficas registrar también:

- Monitor elegido e identificador detectado.
- Geometría y resolución.
- DPI y escala efectiva.
- Ventana objetivo y su identificador.
- Proceso propietario.
- Comprobación del foco antes de enviar entradas.
- Estado de VS Code y de las ventanas preexistentes.
- Resultado de la restauración y limpieza.

No capturar contenido privado innecesario. Utilizar capturas o registros que demuestren la comprobación sin exponer información ajena al objetivo.

# 4. FLUJO OBLIGATORIO DE CADA CHAT

1. Leer el bloque de estado persistente de `prompt_mejoraActual.txt`.
2. Leer COMPLETO `prompt_JARVIS_reglas.txt` y `docs/README.md`, conforme al orden indicado en el prompt principal.
3. Consultar `docs/README_TESTS.md` para las áreas de tests que puedan verse afectadas.
4. Tomar `CURRENT_WORK_UNIT` como objetivo único.
5. Consultar la definición, jerarquía, dependencias, criterios de aceptación y registros pertinentes de la unidad en `prompt_JARVIS_fases_estado.txt`.
6. Comprobar si las dependencias reales necesarias están disponibles. Si no lo están, no fingir su existencia ni implementar anticipadamente otras unidades para sortear el problema.
7. Si `CURRENT_WORK_STATUS` es `PENDIENTE`, cambiarlo a `EN PROCESO` en `prompt_mejoraActual.txt` y guardar ese archivo ANTES de modificar código. Si es `EN PROCESO`, continuar la misma hoja. Si es `PARCIALMENTE IMPLEMENTADA`, continuarla y resolver sus pendientes. Nunca reiniciar ni escoger otra unidad por intuición.
8. Si el ID y el estado se contradicen, no adivinar ni saltar: contrastar el bloque persistente de `prompt_mejoraActual.txt` y solo la parte necesaria del roadmap en `prompt_JARVIS_fases_estado.txt`, registrar la discrepancia y mantener la unidad indicada salvo que se demuestre un error concreto.
9. Leer solo el código necesario. Inspeccionar implementaciones, contratos y dependencias reales antes de crear o modificar funcionalidades.
10. Definir los criterios de aceptación y el plan de pruebas antes de implementar.
11. Implementar exclusivamente la hoja activa.
12. Ejecutar los tests pertinentes, corregir los fallos de tests válidos en producción y realizar las verificaciones unitarias, de integración y reales que correspondan.
13. Comprobar sintaxis, imports, integraciones afectadas y funcionamiento real. No presentar un resultado simulado como una verificación real.
14. Si se ha modificado de forma relevante cualquier fichero dentro de `src/`, revisar si `docs/README.md` debe actualizarse y hacerlo cuando corresponda, conforme a la regla de documentación de la sección 1.
15. Si se ha modificado de forma relevante cualquier fichero dentro de `tests/`, revisar si `docs/README_TESTS.md` debe actualizarse y hacerlo cuando corresponda.
16. Registrar el resultado real en `prompt_JARVIS_fases_estado.txt` y cerrar la unidad conforme a la transición de estado.
17. Actualizar los cuatro campos persistentes de `prompt_mejoraActual.txt` cuando corresponda.
18. Terminar el chat al cerrar la unidad. No abrir, inspeccionar, probar ni implementar la siguiente hoja en ese mismo chat.

No saltar pasos para acelerar el desarrollo. Una implementación sin evidencias suficientes permanece incompleta.

# 5. TRANSICIÓN DE ESTADO Y CONTINUIDAD

- `CURRENT_WORK_STATUS` siempre describe exclusivamente la unidad indicada por `CURRENT_WORK_UNIT`.
- Solo puede haber una hoja en ejecución.
- Al comenzar una hoja `PENDIENTE`, establecer `EN PROCESO` en `prompt_mejoraActual.txt` y guardar ese archivo antes de tocar código.

## 5.1. Cierre satisfactorio

Si se completa la hoja activa:

1. Guardar un único registro final `IMPLEMENTADA` en `prompt_JARVIS_fases_estado.txt`.
2. Asignar `LAST_COMPLETED_UNIT` a esa hoja.
3. Hallar en el roadmap de `prompt_JARVIS_fases_estado.txt` la siguiente hoja realmente pendiente, respetando jerarquía, orden y dependencias.
4. Actualizar `CURRENT_WORK_UNIT` y `CURRENT_PHASE` en `prompt_mejoraActual.txt`.
5. Dejar `CURRENT_WORK_STATUS: PENDIENTE`.
6. Guardar los cuatro campos persistentes y finalizar el chat.
7. No iniciar ni inspeccionar la siguiente hoja.

La siguiente unidad debe permanecer en `PENDIENTE` hasta que un chat dedicado a ella la inicie.

## 5.2. Cierre incompleto o bloqueado

- Si la hoja queda incompleta o bloqueada después de haber iniciado el trabajo, mantener `CURRENT_WORK_UNIT` en esa misma hoja, poner `CURRENT_WORK_STATUS: PARCIALMENTE IMPLEMENTADA` en `prompt_mejoraActual.txt`, registrar los pendientes y no avanzar.
- Registrar qué se ha implementado, qué se ha probado, qué no se ha probado y cuál es la causa concreta del bloqueo.
- No marcar como completada una unidad porque no existan tests fallidos si faltan verificaciones obligatorias.
- Si una unidad se divide, registrar la relación padre-hijas. El puntero debe identificar la primera hija pendiente con estado `PENDIENTE`. El padre no se completa hasta terminar todas sus hijas.
- Si el impedimento aparece antes de iniciar materialmente la unidad, mantener un estado coherente con el trabajo efectivamente realizado y documentar el bloqueo sin inventar
