PROMPT MAESTRO JARVIS — AUTOMEJORA INCREMENTAL

OBJETIVO
JARVIS debe evolucionar de:
intención -> comando -> función -> ejecución
hacia:
intención -> Goal -> Task/HTN -> State/Knowledge -> Graph -> Planner -> Plan -> Executor -> Verification -> State actualizado -> Replan.

REGLAS MAESTRAS
1. La posición actual SOLO sale del bloque de estado persistente. El roadmap no indica la fase actual.
2. Un chat de SuperComplete trabaja UNA sola unidad hoja. No adelantar la siguiente unidad.
3. Una unidad hoja debe caber razonablemente en un chat. Si no, dividirla antes de seguir y registrar las hijas.
4. Al empezar una unidad: EN PROCESO. Al terminar: IMPLEMENTADA. Incompleta: PARCIALMENTE IMPLEMENTADA. Sin trabajo: NO IMPLEMENTADA. Solo una hoja puede estar EN PROCESO.
5. No avanzar hasta completar la hoja activa. Una fase solo se IMPLEMENTA cuando todas sus hojas están completas y main.py queda OK.
6. README.md es el mapa documental. prompt_mejoraActual.txt es la memoria operativa. El código real y los tests son la fuente de verdad técnica.
7. No auditar todo el repositorio. Leer README + estado y abrir solo los archivos necesarios para la unidad activa. En archivos grandes, localizar primero clase/método/símbolo y ampliar solo si hace falta.
8. No crear trabajo para rellenar una lista: no inventar funcionalidades, fases, subfases, archivos, clases, métodos, coordenadas, offsets, tests, métricas o resultados.
9. Las coordenadas/puntos de UI son datos de percepción/calibración. No son inteligencia ni reglas de decisión.
10. No introducir ML, deep learning, RL u otra complejidad solo para aparentar inteligencia. Usar IA/LLM/Vision cuando aporte valor real.
11. Si README, prompt y código discrepan, conservar la discrepancia y comprobar el código necesario. No resolverla por intuición.
12. No pedir archivos indefinidamente. Pedir solo un archivo que sea imprescindible para la unidad activa o para confirmar una discrepancia concreta.
13. No duplicar implementaciones: reutilizar lo que ya existe.
14. No inventar APIs. Adaptar el trabajo a las interfaces reales del repositorio.
15. Para el análisis y la búsqueda de archivos del proyecto, usar siempre `limit=2000`.

TESTS

- No debilitar ni eliminar tests para conseguir PASS: no quitar asserts, ocultar errores, aceptar cualquier resultado, saltar casos o borrar pruebas.
- Modificar un test solo si está objetivamente mal, obsoleto por un cambio legítimo de contrato o contradice los requisitos reales; documentar el motivo.

ESTRUCTURA DE TRABAJO
FASE -> SUBFASE -> SUBSUBFASE (solo si hace falta).
La unidad ejecutable siempre es la hoja más profunda definida.
Si una hoja resulta demasiado grande: dividirla, conservar trazabilidad padre -> hijas y continuar en un chat nuevo.

FLUJO DE CADA CHAT
1. Leer prompt_mejoraActual.txt.
2. Leer TODO README.md.
3. Determinar la primera unidad hoja no completada o la unidad indicada por el estado.
4. Marcarla EN PROCESO y guardar el prompt antes de modificar código.
5. Leer solo el código necesario.
6. Implementar exclusivamente esa unidad.
7. Ejecutar los tests pertinentes.
8. Si fallan y el test es correcto, corregir código.
9. Verificar comportamiento real y compatibilidad.
10. Actualizar estado, README cuando corresponda y prompt.
11. Cerrar el chat antes de abrir el siguiente. Nunca abrir el siguiente prematuramente.

CIERRE DE UNIDAD
Registrar: objetivo, archivos modificados/nuevos, tests y resultado real, main.py si aplica, estado final y pendientes.
No declarar IMPLEMENTADA una unidad si quedan pendientes pertenecientes a ella.

CIERRE DE FASE
1. Todas las hojas IMPLEMENTADA.
2. Actualizar README.
3. Comprobar main.py.
4. Si OK -> PHASE_X_MAIN_START=OK y fase IMPLEMENTADA.
5. Si ERROR -> fase EN PROCESO y corregir.
main.py no necesita ejecutarse al cerrar cada subfase salvo que la integración de esa hoja lo requiera.

CONTEXTO Y SUPERCOMPLETE
Detectar conceptualmente READY, EXECUTING, TOKEN_AVAILABLE y NEED_NEW_CHAT.
Mientras EXECUTING: esperar, no enviar otro prompt, no repetir Send ni cambiar de chat.
Si hay que cambiar de chat: terminar de forma segura la operación actual, guardar código/estado, cerrar y confirmar, abrir nuevo chat y continuar la misma hoja.
No depender de memoria del chat anterior.

MULTIPANTALLA Y AUTOMATIZACIÓN
Debe funcionar con una o varias pantallas, posiciones intercambiadas, ventanas en segundo plano, maximización/restauración y distintas escalas/DPI.
Prioridad: estado real de ventana -> identificación real de aplicación/proceso -> monitor real -> visión -> coordenadas calibradas.
No usar offsets fijos. No mover/cerrar ventanas sin identificar primero la ventana correcta.

ARQUITECTURA FUNCIONAL
- Node representa, según proceda: Goal, Task, Action, Condition, State, Resource, Application, UI element y Result.
- State debe representar progresivamente aplicaciones, ventanas, aplicación/monitor activos, URLs, login, calibración, recursos y estado de SuperComplete.
- Application Knowledge separa conocimiento, capacidades, estados y ejecución.
- Domain Memory separa conversación, aliases, entidades, URLs, preferencias y predicción.
- Graph representa estados, acciones, transiciones, precondiciones, efectos y costes.
- Planner no ejecuta directamente: genera Plan; Executor ejecuta; Verification comprueba; State se actualiza; Replan recalcula cuando el resultado cambia el estado.
- Orden de planificación: determinista -> A* -> replanning -> optimización -> aprendizaje -> automejora.
- Legacy se conserva mientras exista uso: legacy -> Goal -> Planner -> ejecución, sin romper compatibilidad verificada.
- macros_coords.json es conocimiento UI; no contiene la inteligencia completa. Flujo: Planner -> Action -> UI capability -> CoordinateManager -> macros_coords -> Mouse/Keyboard.

CALIBRACIÓN
La calibración es una capacidad, no una colección de funciones específicas por aplicación.
No crear puntos/coordenadas por decisión propia. La visión debe detectar elementos visibles; la calibración persiste el resultado real.
Preparar la aplicación primero (disponibilidad/estado/monitor/ventana). En navegadores ya abiertos, una calibración puede usar una pestaña temporal sin tocar las pestañas del usuario. Solo cerrar recursos creados por JARVIS y restaurar el estado original de ventanas reutilizadas.

ROADMAP MAESTRO
El roadmap es estructura, no estado. No ampliar IDs salvo solicitud explícita o subdivisión técnica realmente necesaria.
Una unidad hoja debe representar UNA modificación conceptual verificable y pequeña. Cuando una tarea implique más de una responsabilidad, dividirla. Preferir hojas que permitan: inspeccionar -> modificar -> probar -> verificar -> cerrar.
